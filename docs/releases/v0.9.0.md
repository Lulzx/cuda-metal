# CuMetal v0.9.0

[Release index](README.md)

CuMetal 0.9.0 is a conformance release. An outside probe corpus,
[Cuport-Matrix](https://github.com/guru-bharadwaj20/Cuport-Matrix), ran 42
plain-CUDA probes through CuMetal and reported five undocumented divergences.
All five are fixed, and on Apple M4 Pro the corpus goes from 27 to 36
bit-exact probes with no undocumented divergence left. The same pass found and
fixed a set of silent wrong answers in the runtime, the driver API and the
compiler, and closes most of the issues opened from downstream users.

## Highlights

- **Shared memory beyond Metal's 32 KB.** Kernels may use CUDA's limits: 48 KB
  per block by default and up to 99 KB after raising
  `cudaFuncAttributeMaxDynamicSharedMemorySize`. Launches that fit in 32 KB
  still use threadgroup memory; larger ones run a spill variant whose shared
  data lives in a per-block device-memory slice, with atomics and barriers
  kept correct. Anything above the limit returns `cudaErrorInvalidValue` and
  runs nothing (#205).
- **Device `assert` reports `cudaErrorAssert` (710).** A failed assert records
  the failure and the next synchronize returns 710, sticky on that stream.
  Kernels that also use `__syncthreads` or warp shuffles still compile; unlike
  CUDA, the failing thread keeps running instead of aborting the kernel.
- **Silent wrong answers fixed.**
  - `__fmul_rn`/`__fadd_rn`/`__fsub_rn` were fused into an FMA (#208).
  - `__shfl_xor_sync` and `__shfl_down_sync` with `width < 32` read the wrong
    lane (#206, #210).
  - Kernels writing through a pointer stored in device memory silently lost
    writes to allocations of 1 MiB or more; every allocation is now resident
    on every queue (#224).
  - Pointers inside data copied between pinned and device memory were not
    rewritten (#225).
  - A raw-PTX module with an FP64 kernel built only its first kernel through
    the driver (#222), and a `float` field in a by-value struct parameter
    arrived as garbage (#231).
  - The exported `cudaGraphInstantiate` and `cuGetProcAddress` had pre-CUDA-12
    signatures, so CUDA 12 callers passed arguments into the wrong slots.
  - A cooperative kernel with a tall grid was split into dispatches that cannot
    be co-resident, making its grid sync wrong.
- **CUDA error codes.** Zero-size launches return
  `cudaErrorInvalidConfiguration` (#207), `cudaEventElapsedTime` on an
  unrecorded or timing-disabled event returns `cudaErrorInvalidResourceHandle`
  (#209), and a kernel with no image returns `cudaErrorNoKernelImageForDevice`
  (#223). A grid sync that never completes now ends in
  `cudaErrorLaunchTimeout` instead of hanging (#175).
- **Intrinsics and PTX.** `__syncthreads_count/_and/_or`, directed-rounding
  half and bfloat16 conversions, `sqrt.rn.f64`/`rsqrt.approx.f64` in every
  FP64 mode (#232), `max.f64`, `shf.clamp`, `brx.idx` jump tables and
  `__nv_longlong_as_double` on the typed PTX path (#218, #221). Device
  `printf` accepts mixed 32/64-bit arguments, prints string literals and
  writes to stdout.
- **Driver API.** NVIDIA's `_v2` entry-point names are exported (#230),
  run-time FP64 PTX stays on the typed JIT with exact argument metadata (#231),
  async memsets are ordered on their stream (#211), and
  `cuGraphInstantiateWithFlags` is added with unsupported flags refused.
- **Libraries.** cuBLAS, cuFFT, cuRAND, cuSPARSE, cuSOLVER and cuDNN calls emit
  `CUMETAL_PROVENANCE` records naming the backend that ran (#215). NVML memory
  comes from the Metal device instead of host RAM (#214). `cudnn.h` defines
  `CUDNN_VERSION` (#212) and Nd tensor descriptors keep their rank (#213).
- **Tooling.** `cumetal doctor` distinguishes JIT-only setups and the Xcode
  26/27 placeholder Metal toolchain (#217); `--compile-timing` reports
  per-phase compile cost (#220); encoders carry kernel names in Instruments
  (#227); `__CUMETAL__`, `__CUMETAL_VERSION__` and `cumetal version --json`
  let downstream code detect CuMetal (#229).
- **Packaging.** An installed toolchain is self-contained: FP64 support
  sources and every public header are installed (#204), and `cumetalc` no
  longer links Homebrew's `libz3`.
- **Launch overhead.** Host submit cost per launch drops 19% (1.15 to 0.94 µs)
  by reading environment switches once (#228).

## Known limits

- On Apple M4 Pro, float arithmetic flushes subnormals to zero regardless of
  compiler flags; the M6 keeps them. See `docs/known-gaps/platform.md`.
- `CUMETAL_USE_METAL_DEVICE_ADDRESSES` is still needed for pointers the host
  writes into managed or mapped memory, and it still serializes streams.
- The LAMMPS release gate was recorded for 0.8.0; its coverage claims are
  re-recorded against the larger 0.9.0 test corpus after release.

## Verification

On Apple M4 Pro, macOS 27.2.1:

- Debug with the binary shim ON, at the release tree: **499 of 499** fast
  tests (`ctest -LE slow`) passed.
- At `761ca9e` (the conformance fixes, before the downstream-issue batch):
  469 of 469 fast tests with the shim ON, 466 of 466 with it OFF, and every
  slow-labelled test except the cuda-samples sweep passed, including the
  PhysX PBD, GRB and corpus gates.
- cuda-samples: 81 of 83 enrolled samples are gated as passing.
  `cdpQuadtree` and `cdpAdvancedQuicksort` are recorded as `no-lowering`: they
  fail at every release back to v0.7.0 when rebuilt with Homebrew LLVM 23, so
  the 83/83 figure since the LLVM upgrade was a manifest expectation, not a
  measured run. `UnifiedMemoryPerf` can hit a GPU-hang timeout when the
  machine is heavily loaded; it passes on an idle machine.
- Cuport-Matrix, all 42 probes on M4 Pro: 36 bit-exact, 2 within tolerance,
  1 documented divergence (FP64 `fast48`), 2 refusals (dynamic parallelism,
  an over-sized cooperative grid) and 1 known platform limit (float
  subnormals). v0.8.0 scored 27 bit-exact with 5 undocumented divergences.
- The LAMMPS release gate was not re-run; its coverage assertions in
  `.claimwire` fail until it is re-recorded against the larger corpus.
